## Research Question

What server architecture — state-management approach, MCP primitive usage (Tools / Resources / Prompts), tool-surface design, and workflow-guidance pattern ("Guide" vs "Worker") — should a production Go MCP server built on the Tier‑1 `github.com/modelcontextprotocol/go-sdk` use to run the Vivechak research-pipeline workflow (workspace initialization, session-DAG tracking, output validation, and agent guidance) reliably across Claude, Cursor, Antigravity, and VS Code?

*Note on context: Vivechak (fetched directly from `github.com/bhaskarjha-dev/vivechak`) is currently a manual methodology — a generator prompt plus four Markdown+YAML templates that a human copies into a project's `research/` folder and drives by hand. The server this research informs corresponds to the project's own Roadmap Phase 5, "Vivechak Engine — agentic pipeline execution," which does not yet exist. Facts about Vivechak's own design (its principles, schemas, rubric) are cited below as primary-source project context, graded like any other claim, but they are evidence about *what the target system needs*, not general evidence about MCP architecture.*

## Key Findings

- MCP is mid-rewrite toward a **stateless-first protocol** (SEP‑2575, "Final," landing by spec version 2026‑07‑28): the design explicitly ranks *stateless requests* > *explicit state references/handles* > *true statefulness*, and names load‑balancer incompatibility, lost sessions on crash, and server‑side session bookkeeping as the costs of statefulness (Grade A · corroborated · fresh · direct | fetched).
- The spec's own non-normative "Stateful Tools" guidance (2026‑07‑28) already prescribes the pattern Vivechak needs: a creation tool returns an opaque handle, later calls pass that handle back, and the server — not the protocol — owns the state behind it (Grade A · single · fresh · direct | fetched). A workspace's filesystem path can *be* that handle.
- Tools are model‑controlled and are the one primitive every mainstream client invokes autonomously; Resources are spec‑defined as **application‑driven** and in practice require a manual action in at least one major client (VS Code's "Add Context → MCP Resources"), and Prompts are user‑invoked slash‑commands, not something an autonomous agent reaches for on its own (Grade A · corroborated · fresh · direct | fetched).
- GitHub's own production Go MCP server — the flagship real-world example in this space — built agent‑runtime "dynamic tool discovery" meta‑tools in 2025, then **deleted the feature in May 2026** as tech debt, while separately solving the underlying "too many tools" problem (102 tools / 64.6k tokens by default) with static, operator‑configured toolset curation instead (Grade A · corroborated · fresh · direct | fetched). This is real evidence against building *self-discovery machinery* into the tool surface — a distinct question from whether tool *results* should carry workflow guidance.
- The official Go SDK holds **Tier 1** status (100% conformance, ≤2‑business‑day issue triage) alongside the TypeScript, Python, and C# SDKs, and is the SDK GitHub itself migrated `github-mcp-server` onto in December 2025, explicitly to "keep up with new features and changes to the MCP spec" (Grade A · corroborated · fresh · direct | fetched).
- Long-running work has two spec-native answers of different weight: core-spec **progress notifications** on a still-open call (broadly supported, simple) and the **Tasks extension** (`working → input_required → completed/failed/cancelled`, durable across disconnects) for genuinely async or human‑gated work — but Tasks is an *extension*, and "host support varies by client" (Grade A · single · fresh · direct | fetched), so it cannot be the only mechanism a client-portable server relies on.
- Vivechak's own design language independently converges on the same answer as the protocol: Principle P6 mandates "Hybrid Markdown + YAML frontmatter" artifacts, P5 says compose commodity infrastructure and hand‑build only "proprietary domain intelligence, core state machines," and P8 demands the pipeline itself stay a **Constrained DAG**, not "rigid stage gates" — which argues against a maximal, hard‑enforcing Guide implementation as much as it argues for one (Grade A · single · fresh · direct | fetched, project-context).

## Recommendation

**Architecture: a "Guided Worker."** Build small, single-responsibility tools — Worker-shaped, each with one clear precondition and one clear effect — but make every tool's *result* carry the workflow guidance a "Guide" pattern would otherwise hide in server-side control flow: current DAG status, which sessions are next-eligible, why a call was rejected, and what to call next. Put the intelligence in the *data returned*, not in a hidden state machine that silently blocks "wrong" calls. This is the synthesis that survives the disconfirming evidence below (see Detailed Findings §10): a maximal, hard-gating Guide contradicts Vivechak's own "not rigid stage gates" principle and the protocol's "statefulness as a last resort" principle; a pure, unguided Worker contradicts Vivechak's entire reason for existing (preventing agents from "hallucinating structure"). Classify this as a **two-way door** for D‑001 — it governs response *shape*, not wire format, and can be tightened or loosened per tool without a migration.

**State management: the `research/` directory is the database.** Canonical state is the Markdown+YAML files Vivechak already mandates (`RESEARCH-PIPELINE.md`, `DECISIONS.md`, `sessions/*.md`); the server parses and writes them directly rather than shadowing them in a separate store. The workspace's absolute path is the explicit "state reference" the spec's Stateful-Tools guidance calls for — pass it as a tool argument on every call (Roots is deprecated for this purpose per SEP‑2577; do not rely on it). Do **not** hold DAG/session state only in server memory: stdio servers are commonly one process per client connection, so in-process state cannot be seen by a second agent (or by the same agent after a restart) and directly contradicts SEP‑2575's ranking. Do **not** introduce a database at this scale: it would create a second, binary, non-diffable source of truth alongside files Vivechak's own contract already requires to be human‑ and git‑readable, for a workload (one project, occasionally parallel Layer‑0 sessions) that plain files with disciplined atomic writes and file locks handle fine. See the weighted comparison in §2. This is a **two-way door**: an internal, in-memory index rebuilt from files at startup is a pure performance optimization that can be added later without changing the on-disk contract or any tool's interface.

**Primitives: everything the agent must act on is a Tool.** Resources are supplementary, not load-bearing — use `file://` or a custom `vivechak://` scheme to expose the same research files for optional context-inclusion (a human browsing `resources/list` in an Inspector or a client that does automatic inclusion), but never make a required capability reachable *only* through a Resource, because at least one mainstream client requires a manual click to surface them and the spec does not mandate any particular resource UI. Skip Prompts for the core loop for the same reason it's user-invoked, not agent-invoked; a small number of Prompts as optional convenience slash-commands (e.g., "start a session") is fine but never load-bearing.

**Tool design.** Roughly 6–10 tools, snake_case, verb‑first or resource‑scoped consistently (Anthropic's own tool-writing guidance and the MCP tool-name rules both point the same way): e.g. `workspace_init`, `dag_status`, `session_next`, `session_validate`, `decision_record`, `gate_check`. Use the Go SDK's typed generics (`mcp.AddTool[Input, Output]`) with `jsonschema` struct tags as the description surface, and set an `outputSchema` on every tool so results are `structuredContent`, not prose the agent must re-parse. Report validation failures as **Tool Execution Errors** (`isError: true` with actionable text), never as JSON-RPC protocol errors — the spec's own rationale is that only the former gives a model something it can act on to retry. A minimal illustrative sketch:

```go
type ValidateSessionInput struct {
    WorkspacePath string `json:"workspace_path" jsonschema:"absolute path to the research/ directory"`
    SessionID     string `json:"session_id" jsonschema:"e.g. R-02"`
}

type ValidateSessionOutput struct {
    Valid        bool     `json:"valid"`
    Errors       []string `json:"errors,omitempty"`
    NextEligible []string `json:"next_eligible_sessions,omitempty"` // the "guide" payload
}

func ValidateSession(ctx context.Context, req *mcp.CallToolRequest, in ValidateSessionInput) (
    *mcp.CallToolResult, ValidateSessionOutput, error,
) {
    // parse the session file at {WorkspacePath}/sessions/{SessionID}-*.md,
    // check YAML frontmatter + the 7-section skeleton + the quality rubric,
    // return isError:true with a concrete, fixable message on failure.
}

mcp.AddTool(server, &mcp.Tool{
    Name:        "session_validate",
    Description: "Validate a completed research session file against the required schema and evidence-quality rubric before it can inform a decision.",
}, ValidateSession)
```

**Long-running operations.** Baseline: the explicit-handle pattern itself (a `session_validate` call that might take a while returns immediately with a handle; a `session_validate_status` call polls it) works on every client with no extension required. Layer core-spec progress notifications (`ReportProgress`) on top for calls that stay open. Advertise the Tasks extension capability *only* additively, and confirm the calling client declared support before ever returning a `CreateTaskResult` — never make it the only path.

**Testing.** Three layers: (1) Go unit tests against `mcp.NewInMemoryTransports()` — a real `Client` and `Server` wired through in-process pipes, no subprocess, so tool handlers are tested exactly as the wire protocol will exercise them; (2) `npx @modelcontextprotocol/inspector --cli <binary> --method tools/call ...` scripted in CI as a black-box smoke test across `tools/list` and each tool; (3) a small fixture library of "golden" and "broken" `research/` workspace trees (valid DAG, malformed frontmatter, missing evidence grade, circular dependency) that `session_validate` and `dag_status` are run against, since the entire point of this server is judging whether *files*, not just JSON arguments, are well-formed.

## Alternatives Considered

- **Pure Worker (atomic, unguided tools; all sequencing logic lives in the agent's own prompt/system instructions).** Rejected: this is precisely the failure mode Vivechak's founding philosophy names — "unstructured 'just ask the AI' research is systematically vulnerable to confirmation bias" and agents "hallucinating structure" — so a server that hands back bare data with no state/next-step signal reproduces the exact problem the framework exists to fix (Grade A · single · fresh · direct | fetched, project-context).
- **Maximal Guide (server-side state machine that hard-rejects any "out of order" tool call).** Rejected as the default: Vivechak's own DAG topology is explicitly "unblocked by default," with only *hard* information dependencies blocking execution and *soft* ones merely informing — a state machine that hard-blocks by default inverts this and would also fight the framework's own "Adaptive Checkpoints" and "Progressive Elaboration" provisions, which assume the DAG shape can legitimately change mid-flight (Grade A · single · fresh · direct | fetched, project-context). Reserve hard blocks for genuine data unavailability (you cannot validate a file that doesn't exist yet), not policy.
- **In-memory server state as the source of truth.** Rejected: contradicts SEP‑2575's explicit statelessness ranking, breaks the moment two clients (say, Claude Code and Cursor) point at the same workspace, and does not survive the process restarts that are routine for stdio-launched servers (Grade A · corroborated · fresh · direct | fetched).
- **Embedded database (SQLite) as the source of truth.** Rejected for now, not permanently: scores second in the weighted comparison (§2) mainly because it introduces a second, non-diffable representation alongside files Vivechak's contract already requires to be Markdown+YAML, for a concurrency need (occasional parallel Layer‑0 sessions) that file locking already covers. Revisit if the roadmap's own "Phase 6: multi-agent debate" materializes and concurrent writers become the common case rather than the exception — see Open Questions.
- **Expose pipeline/DAG state primarily through MCP Resources rather than Tools.** Rejected as the primary channel: Resources are spec-defined as application-driven, and VS Code's own documentation shows resource inclusion is a manual "Add Context" action, not something an autonomous agent reaches for — a required capability placed only behind a Resource risks being invisible to the agent in some clients (Grade A · corroborated · fresh · direct | fetched). Kept as a *supplementary* read surface.
- **Drive the whole flow through MCP Prompts (slash-command templates).** Rejected as the primary mechanism: Prompts are explicitly user-controlled/user-invoked in the spec and in every client surface found (VS Code's `/<server>.<prompt>` syntax; Cursor lists Prompts as "templated messages... for users"), which is the wrong locus of control for an agent that should decide on its own when to call `session_next` (Grade A · corroborated · fresh · direct | fetched).
- **`mark3labs/mcp-go` instead of the official SDK.** Rejected: it is explicitly acknowledged by the MCP org as one of the SDKs that "inspired the development" of the official one, describes its own exported API as unstable, and is exactly what GitHub's flagship server migrated *away from* in favor of the official, Tier‑1, spec-current SDK (Grade A · corroborated · fresh · direct | fetched). Only defensible if a project is already deep in its API and cannot yet afford a migration.
- **Agent-runtime dynamic tool-set discovery (meta-tools like `enable_toolset`) to manage a large tool surface.** Rejected given Vivechak's likely tool count (6–10, not 100+): GitHub built and then removed exactly this for its own server, citing "real complexity" — a parallel registration path, extra config plumbing, and a larger conformance/CI matrix — as not worth it (Grade A · single · fresh · direct | fetched). Revisit only if the tool count grows far beyond what a single default toolset can hold.

## Detailed Findings

### 1. The protocol is mid-rewrite, and the direction matters more than any single mechanism

The MCP specification current as of this research (`2026-07-28`) is not a stable resting point; it is one snapshot in an active, fast-moving rewrite. Three "Final"-status SEPs fetched directly from `modelcontextprotocol.io` define the trajectory an architect needs to build *with*, not against:

- **SEP‑2575, "Make MCP Stateless"** removes the mandatory `initialize` handshake entirely and replaces it with per-request protocol version, capabilities, and client identity carried in `_meta`. Its stated design order of preference is explicit: prioritize stateless requests; where that's not practical, prefer passing *references* to state on every request; treat true, long-lived stateful connections as "a last resort" (Grade A · corroborated · fresh · direct | fetched). The rationale section is concrete about why: a client's session tied to one server instance defeats simple load balancing, a crashed instance loses that state, and both client and server carry real implementation burden managing session lifecycle.
- **SEP‑2567, "Sessionless MCP via Explicit State Handles,"** referenced by SEP‑2575 as the SEP that replaces protocol-level sessions with explicit handles, confirming this isn't an isolated opinion but a coordinated direction across the spec (Grade A · single · fresh · direct | fetched — title and cross-reference confirmed; full SEP text not independently fetched in this session).
- **SEP‑2577, "Deprecate Roots, Sampling, and Logging,"** removes three features on adoption/complexity grounds. Sampling is explicitly called out as the most security-sensitive of the three ("creates attack surface for prompt injection and data exfiltration"); Roots is dropped because its semantics were only ever advisory and low-adoption; Logging because stderr (stdio) and OpenTelemetry already do the job better than a protocol-level channel (Grade A · single · fresh · direct | fetched). Practically: don't design the workspace-context mechanism around Roots, don't reach for Sampling if the server ever needs an LLM call (out of scope here anyway per the brief), and log to stderr or OpenTelemetry, not `logging/setLevel`.

Layered on top, the **Multi Round-Trip Requests (MRTR)** pattern (new in 2026‑07‑28) lets any `tools/call` or `resources/read` return an `InputRequiredResult` instead of completing, triggering a sub-exchange (often an elicitation) before the client retries with `inputResponses` and a server-supplied `requestState` token (Grade A · single · fresh · direct | fetched). This is a protocol-native way to handle "I need one more piece of information before I can finish this validation" without the server inventing its own out-of-band clarification mechanism.

**Implication for Vivechac:** every mechanism recommended below (explicit handles, MRTR, Tasks) is not a workaround for MCP's limitations — it *is* where the spec is headed. An architecture that leans on implicit session state would be swimming against a current the protocol's own maintainers are actively strengthening.

### 2. State management: file-based artifacts, explicit handle, weighted comparison

The spec's own "Stateful Tools" section (2026‑07‑28, `server/tools.md`) is direct: MCP has no protocol-level session, so a server "cannot rely on implicit per-connection state to relate one tool call to the next." Its worked example — a `create_basket` tool returns a `basket_id`; `add_item` takes that `basket_id` as an argument; the model carries the reference forward — is architecturally identical to "a `workspace_init` tool returns (or the agent already knows) a workspace path; every later tool takes that path as an argument" (Grade A · single · fresh · direct | fetched). The spec's own design considerations for handles apply directly: state the retention/lifetime policy in the tool's description, return a clear, actionable error on an expired/unknown handle so the model can recover, and — since Vivechak's server runs unauthenticated, locally, for a single user — favor a transparent handle (the real path) over an opaque token, since there's no capability boundary a path could leak across.

Applying Vivechak's own Weighted Evaluation Protocol (its FRAMEWORK.md §6.4) to the state-management decision, with criteria derived from this specific project's constraints:

| Criterion | Weight | Rationale |
|---|---|---|
| Survives restart/crash | 0.20 | stdio servers are commonly one process per client session; losing DAG state on every restart is a non-starter for a multi-day pipeline |
| Visible across agents (Claude, Cursor, Antigravity, VS Code) | 0.20 | the brief's own target-client list; state must be legible to whichever tool the user opens next |
| Fits Vivechak's existing artifact contract (Markdown+YAML, git-diffable) | 0.20 | P6 already mandates this format for every research artifact; a second, shadow format creates two sources of truth |
| Operational simplicity for a small/solo OSS project | 0.15 | P5 argues for commodity composition; today's repo has 0 stars/forks — new infrastructure is a real cost, not a rounding error |
| Alignment with MCP's stateless-first direction (§1) | 0.15 | building against the protocol's own stated direction is a foot-gun as the spec matures |
| Safe concurrent writes (Layer‑0 sessions can run in parallel) | 0.10 | the framework explicitly designs for parallel session execution |

| Option | Restart-safe | Cross-agent | Fits contract | Simplicity | Stateless-aligned | Concurrency | **Weighted** |
|---|---|---|---|---|---|---|---|
| **File-based (`research/` as source of truth)** | 5 | 5 | 5 | 4 | 5 | 3 | **4.65** |
| Embedded DB (SQLite) | 5 | 4 | 2 | 3 | 4 | 5 | 3.75 |
| In-memory (server process) | 1 | 1 | 1 | 5 | 1 | 2 | 1.70 |

*Sensitivity check: shifting the highest-weighted criterion ("fits existing contract," the most Vivechak-specific of the six) by ±20% moves the file-based score between 4.49 and 4.81 and the SQLite score between 3.67 and 3.83 — file-based stays clearly ahead in both directions, so the recommendation is not weight-sensitive. In-memory does not become competitive under any plausible reweighting.*

This is qualitative-and-quantitative agreement: the file-based option wins on the criteria that are hardest to reverse (durability, cross-agent visibility, contract fit) and only loses ground on concurrency, which disciplined atomic writes (write-to-temp-file-then-rename) and an advisory lock file solve without a database engine. An in-process cache rebuilt from disk at startup — never the source of truth — is a reasonable later optimization for `dag_status` if parsing every Markdown file on every call becomes measurably slow; this is a two-way door and does not need to be decided now.

### 3. Resources vs. Tools vs. Prompts: what the spec says, and what clients actually do

The spec's three primitives have genuinely different control models, confirmed directly from the 2026‑07‑28 specification text:

- **Tools are model-controlled**: "the language model can discover and invoke tools automatically based on its contextual understanding" (Grade A · single · fresh · direct | fetched).
- **Resources are application-driven**: "host applications determining how to incorporate context based on their needs" — the spec's own examples of what a host *might* do are a picker UI, search/filter, or heuristic auto-inclusion, explicitly leaving the mechanism up to each client (Grade A · single · fresh · direct | fetched).
- **Prompts** are not detailed at length in what this session fetched directly, but every client surface found treats them as user-invoked templates, not agent-invoked (see below).

That distinction is not theoretical — it was confirmed against real client behavior for two of the four target agents:

- **VS Code** (fetched, official docs, dated 2026‑09‑16): Resources require the user to select "Add Context → MCP Resources" or run the `MCP: Browse Resources` command; Prompts are invoked by typing `/<server>.<prompt>` in the chat box. Neither is something the model reaches for unprompted (Grade A · single · fresh · direct | fetched).
- **Cursor** (fetched, official docs): lists Tools, Prompts, Resources, and Elicitation as all "Supported," but its own framing of Prompts is "templated messages and workflows **for users**" and of Resources as data "that can be read and referenced" — again, human-mediated inclusion, not autonomous agent action (Grade A · single · fresh · direct | fetched).

**Implication:** anything the Vivechak server needs the agent to do *by itself* mid-task — check DAG status, validate a file, record a decision, ask "what's next" — has to be a Tool, full stop. Resources are a legitimate, low-cost way to expose the same underlying files (e.g., a `vivechak://workspace/{path}/decisions` URI, or just plain `file://` URIs into `research/`) for a human or a client with automatic-inclusion heuristics, and they compose well with the "Resource Links" mechanism (a tool can return a `resource_link` pointing at the file it just validated, so the client can offer to open it) — but nothing required should live *only* behind a Resource.

### 4. Tool naming, description, and surface-area discipline

The spec's normative tool-name rules (2026‑07‑28, effectively codifying what was proposed as SEP‑986) are specific: 1–128 characters, case-sensitive, restricted to `A-Za-z0-9_-.`, no spaces, and unique **within a server** — the spec explicitly declines to guarantee cross-server uniqueness and puts disambiguation on the client/proxy layer, naming "prefixing tool names with a server identifier" as the suggested client-side strategy rather than mandating server-side self-namespacing (Grade A · single · fresh · direct | fetched). In practice, though, Anthropic's own applied-AI guidance for building tools recommends namespacing anyway — grouping related tools under a common prefix by service or by resource (its own examples: `asana_search`, `asana_projects_search`) — because it also helps *the model's own reasoning*, independent of what any given client does for collision avoidance, and the same post notes prefix- vs. suffix-based namespacing has "non-trivial effects" on their internal tool-use evaluations without specifying which direction is better in general (Grade A · single · fresh · direct | fetched). Net: prefix Vivechak's tools consistently (e.g., a shared verb/resource vocabulary such as `workspace_init`, `dag_status`, `session_validate`) for the model's benefit even though the *client* is nominally responsible for cross-server disambiguation.

The "too many tools" failure mode is not hypothetical; it's measured. GitHub's own MCP server carried 102 tools consuming 64.6k tokens of context by default before a September 2025 change, and the team's own stated reasons for cutting the default were "tool selection degradation" and "excessive context," not a theoretical concern (Grade A · single · fresh · direct | fetched). Their fix was **not** to add more tools that help the agent search for tools — that path (`--dynamic-toolsets`, three meta-tools: `list_available_toolsets`, `get_toolset_tools`, `enable_toolset`) was tried, shipped as a local-only beta for roughly a year, and then removed in May 2026 as "tech debt" carrying "real complexity" for a feature usage apparently didn't justify (Grade A · single · fresh · direct | fetched, from the removal PR's own description). The fix that stuck was **data-driven default curation**: ship the five most-used toolsets on by default, make the rest opt-in via a `--toolsets` flag or (for the remote/HTTP server) an `X-MCP-Tools` header, and keep splitting large toolsets into smaller ones as usage data suggests. Anthropic's separate context-engineering guidance converges on the same test: "If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better" (Grade A · single · fresh · direct | fetched). Vivechak's likely tool count (6–10) is well under the range where this became a problem for GitHub, but the naming discipline and single-responsibility framing apply regardless of scale.

### 5. Error handling and validation patterns

The spec draws a sharp, load-bearing line between two error mechanisms, and getting this right matters more for Vivechak than for almost any other kind of server, because *validating a research output* is a core responsibility:

- **Protocol errors** (standard JSON-RPC error objects, e.g. `-32602` for a malformed request or unknown tool) are for failures the model is unlikely to be able to fix by trying again with different arguments.
- **Tool execution errors** (`isError: true` inside an otherwise normal tool result) are for "actionable feedback that language models can use to self-correct and retry" — the spec's own example is a validation failure ("Invalid departure date: must be in the future") delivered this way, not as a protocol error (Grade A · single · fresh · direct | fetched).

For `session_validate` and any similar tool, a failed schema check, a missing evidence grade, or a broken cross-reference to a decision ID should always come back as `isError: true` with a specific, fixable message (ideally referencing the exact rubric line that failed, since Vivechak's own quality rubric — evidence density, disconfirming evidence present, reversal triggers stated, and so on — is itself an enumerable checklist a tool can walk mechanically) — never as a raw JSON-RPC error, which the spec itself notes clients are "less likely" to successfully recover from. `outputSchema` should be set so results are `structuredContent` (a typed pass/fail plus a list of violations) rather than a paragraph of prose the calling agent has to re-parse to decide what to do next. On the resource side, the spec is explicit that a resource that doesn't exist must return `-32602` (with `-32002` accepted for back-compat) and must never return an empty `contents` array, since that's ambiguous between "exists but empty" and "doesn't exist" — relevant if the server ever exposes `research/` files as Resources rather than only through Tools.

### 6. Long-running and multi-step operations

Three spec-native mechanisms exist at three different weights, and they're complementary rather than competing:

1. **Progress notifications** — the most universally usable. A tool call stays open; if the client supplied a `progressToken`, the server calls back with incremental progress (percentage, a status message) on the same connection. Confirmed directly in a real Go-SDK-based codebase review: `req.Params.Meta.ProgressToken`, `req.ReportProgress(ctx, &mcp.ProgressParams{...})` (Grade B · single · fresh · direct | fetched — from a dependency-review writeup showing real code, not the official spec page itself, hence B not A). This is the right default for "validating a large research output might take a few seconds to tens of seconds."
2. **MRTR / `InputRequiredResult`** — for "I can't finish this call without one more piece of information," not for raw duration. Useful if `session_validate` or `gate_check` ever needs to ask a clarifying question mid-call rather than simply failing.
3. **The Tasks extension** — for work that may genuinely outlive a connection (minutes+, or needs to survive a disconnect/reconnect). A supported request returns `resultType: "task"` with a durable `taskId`; the client polls `tasks/get` (or subscribes to `notifications/tasks`) until a terminal state. Its own documentation is explicit that this is an *extension*, opt-in on both sides, and that "host support varies by client" (Grade A · single · fresh · direct | fetched) — this session did not verify current per-client Tasks support for Claude, Cursor, Antigravity, or VS Code specifically (flagged in Open Questions).

**Recommendation restated with mechanism:** implement the explicit-handle poll pattern as the baseline (works everywhere, no extension needed — this is literally the same "Stateful Tools" pattern from §2, just applied to an operation instead of a workspace), add progress notifications for free since the Go SDK exposes them directly, and treat Tasks as a pure enhancement gated on the calling client having declared the capability.

### 7. Go SDK idioms and the production Go ecosystem

The official SDK (`github.com/modelcontextprotocol/go-sdk`, Apache‑2.0/MIT, ~5k GitHub stars, 755 commits, "maintained in collaboration with Google") is built around Go generics rather than a builder pattern: `mcp.NewServer(&mcp.Implementation{...}, nil)`, then `mcp.AddTool(server, &mcp.Tool{Name, Description}, handlerFunc)` where `handlerFunc` has the signature `func(ctx, *mcp.CallToolRequest, TypedInput) (*mcp.CallToolResult, TypedOutput, error)` and input/output types carry `json` and `jsonschema` struct tags that become the tool's schema and per-field descriptions directly (Grade A · single · fresh · direct | fetched). Other confirmed idioms directly relevant here: `Client.AddRoots` / `ServerSession.ListRoots` for the (now-deprecated) roots mechanism; `Server.AddPrompt` / `ClientSession.GetPrompt` for Prompts; sending- and receiving-middleware chains (`Client.AddSendingMiddleware`) for cross-cutting concerns like injecting a progress token; and a distributed/stateless deployment example shipped in the SDK's own `examples/server/distributed` directory, tied to the requirement that Streamable HTTP at protocol version 2026‑07‑28 only be served in `Stateless = true` mode (Grade A · single · fresh · direct | fetched) — worth reading later if Vivechak ever offers a remote/team deployment mode, though out of scope for a local, single-user server today.

The version-compatibility table is itself useful evidence of Tier‑1 maintenance discipline: SDK v1.7.0+ already supports the 2026‑07‑28 spec as its latest target while retaining four prior spec versions back to 2024‑11‑05 (Grade A · single · fresh · direct | fetched) — a new server can target the newest spec without stranding older clients.

**Production example: `github/github-mcp-server`.** This is the most instructive real Go MCP server for a workflow-shaped tool surface, for two reasons already used above: it fully migrated from the community `mark3labs/mcp-go` SDK to the official one in December 2025 specifically to track spec changes (Grade A · single · fresh · direct | fetched), and its public PR/issue history is an unusually well-documented natural experiment in tool-surface scaling (§4). Its toolset mechanism — named groups of related tools, gated by a comma-separated allow-list flag or environment variable, with an `all` escape hatch and an explicit rule that read-only mode always wins over an explicit tool request — is a directly reusable pattern if Vivechak's tool count ever grows enough to need grouping (Grade A · single · fresh · direct | fetched). For comparison, `mark3labs/mcp-go` — the predecessor SDK, "originally authored by Ed Zynda" and explicitly credited by the official SDK's own README as one of the projects that "inspired" it — remains usable and lower-boilerplate for very simple servers, but its own README currently describes its exported API as one that "should currently be considered unstable" (Grade A · single · fresh · direct | fetched), which is a real cost for a server meant to be a stable dependency of other people's agent workflows.

### 9. Testing strategy

Three complementary layers, aimed at three different kinds of bug:

1. **Protocol-level unit tests, in Go, via `mcp.NewInMemoryTransports()`.** Confirmed directly from the SDK's generated package documentation: `func NewInMemoryTransports() (*InMemoryTransport, *InMemoryTransport)` returns a connected pair, so a test can spin up a real `mcp.Server` and a real `mcp.Client` in the same process, call `tools/list` and `tools/call` exactly as a real client would, and assert on the actual wire-shaped result — no subprocess, no stdio, fast enough to run on every commit (Grade A · single · fresh · direct | fetched). This is the right layer for "does `session_validate` correctly reject a session file with a missing evidence grade."
2. **Black-box smoke tests via the official MCP Inspector's CLI mode**, scriptable in CI: `npx @modelcontextprotocol/inspector --cli <path-to-binary> --method tools/list` (and `--method tools/call --tool-name ... --tool-arg ...`), documented as built specifically for "CI, shell pipelines, and coding agents" as opposed to the Inspector's default browser UI (Grade A · single · fresh · direct | fetched). This layer catches packaging/startup problems (wrong binary path, missing env var, bad JSON schema) that in-process tests can't see because they never actually spawn the compiled binary.
3. **Fixture-based workspace tests**, specific to this server's domain: a small library of realistic `research/` trees — one fully valid, one with a broken DAG (circular hard dependency), one with a session file missing required frontmatter, one with an uncorroborated Grade D claim underpinning what's declared a one-way-door decision — run through `dag_status`, `session_validate`, and `gate_check` and asserted against expected pass/fail output. Cross-SDK precedent for the general "test through an in-process transport rather than a real subprocess" pattern was also found in the Python SDK (`create_connected_server_and_client_session`) and C# SDK (paired in-memory pipes wrapped in the stdio transport types) (Grade B · corroborated · fresh · indirect | fetched) — useful corroboration that this is a convention across the whole MCP SDK family, not a Go-specific accident.

The MCP project also publishes a separate, spec-level **conformance test suite** (`github.com/modelcontextprotocol/conformance`) used to assign SDK tiers; that's a test of the *SDK*, not of Vivechak's server, but it's worth knowing it exists as the yardstick the Go SDK itself is held to (Grade A · single · fresh · indirect | fetched).

### 10. The "Guide" vs. "Worker" question, and the disconfirming evidence

Working definitions used in this session, since no prior write-up of "Approach A/B" was available to fetch: a **Worker** server exposes atomic, stateless-feeling operations and trusts the calling agent's own reasoning (system prompt, planning) to sequence them correctly; a **Guide** server tracks workflow state itself and actively directs the agent — telling it what step it's on and what to call next, and typically rejecting calls that are "out of order."

**Evidence in favor of Guide-like elements:**
- Vivechak's entire reason for existing is exactly the failure mode a pure Worker would reproduce: per its own README and FRAMEWORK.md, the "most load-bearing finding" of the project's meta-research is that unstructured, ungrounded AI research is "systematically vulnerable to confirmation bias," and its templates are explicitly designed so an agent "follow[s] the exact format, methodology, and checklist without hallucinating structure" (Grade A · single · fresh · direct | fetched, project-context). A server that returns bare data with no indication of pipeline state asks the agent to reconstruct exactly the structure Vivechak exists to impose externally.
- The protocol itself now has first-class support for exactly this shape of interaction — explicit state handles (§2), MRTR's mid-call clarification (§1), and Tasks' `input_required` status (§6) are all spec-native ways to let a tool actively steer a multi-turn exchange rather than just answering one question at a time.

**Disconfirming evidence, actively sought as instructed:**
- The single clearest counter-example is GitHub's own removal of dynamic tool discovery (§4): a mechanism that let the *agent* drive discovery/enablement of tool groups at runtime — arguably a Guide-flavored pattern applied to the tool surface itself — was built, kept as a local-only beta for roughly a year, and then deleted as tech debt that "carried real complexity" disproportionate to its value, in favor of a much simpler, static, operator-configured alternative (Grade A · single · fresh · direct | fetched). This is scoped evidence: it argues against *agent-runtime meta-tooling for discovering tools*, not against guidance carried in ordinary tool *results* — conflating the two would overstate what was found — but it is a real, recent, production data point that more machinery in this direction has a cost that a leading team judged not worth paying.
- SEP‑2575's explicit hierarchy — "treat statefulness as a last resort" — is a protocol-level design philosophy that cuts directly against any server architecture whose primary value proposition is *being* a stateful guide. It does not forbid state; it demands that each piece of state earn its complexity.
- Vivechak's own DAG topology is deliberately **not** a rigid state machine: "every research session defaults to unblocked... unless an explicit hard information dependency is declared," and the framework has explicit "Adaptive Checkpoints" and a "Progressive Elaboration Protocol" for when the plan itself needs to change mid-pipeline (Grade A · single · fresh · direct | fetched, project-context). A maximal Guide implementation that hard-enforces one linear order would be more rigid than the methodology it's meant to serve — an internal contradiction, not just an external one.
- More generally, none of the production Go servers examined in this session (github-mcp-server, the gh-aw-reviewed server) implement a hard workflow-enforcement layer; both expose atomic tools and use Resources/progress/annotations for context, which is closer to Worker-with-context than Guide.

**Resolution:** the "Guided Worker" recommended above is the position this evidence actually supports — atomic tools (Worker shape, satisfying the disconfirming evidence and SEP‑2575) whose results carry explicit guidance data (satisfying Vivechak's founding rationale and the spec's own state-handle/MRTR primitives), with hard blocks reserved for genuine data unavailability rather than policy enforcement (satisfying the DAG's own "soft dependency" design). This is not a compromise reached by splitting the difference; each half of it is independently the better-supported answer to a narrower question the evidence actually distinguishes.

## Open Questions & Risks

- **Antigravity's MCP config path is contested in current documentation** (`~/.gemini/config/mcp_config.json` vs. `~/.gemini/antigravity/mcp_config.json`), and this session found no example of a confirmed local/stdio server entry for Antigravity specifically (only remote/OAuth examples using `serverUrl`). *Risk: medium, easy to fix* — verify directly against the currently-installed Antigravity version before publishing setup instructions; do not assume either path is stable given how young the product line is.
- **Tasks-extension client support was not verified per target client.** The extension's own docs state support "varies by client," and this session did not fetch the live client-compatibility matrix values for Claude, Cursor, Antigravity, or VS Code. *Risk: low* if the recommended baseline (explicit-handle polling, which needs no extension) is implemented first and Tasks is layered on as a pure enhancement — but worth a direct check (`modelcontextprotocol.io/clients` or the `canimcp.dev` community matrix, discovered but not queried in depth this session) before depending on it for anything.
- **Path/workspace security.** The server's core job is reading and writing inside a user-designated project directory based on tool arguments (a workspace path, a session ID used to build a filename). The spec's own Resources security guidance is explicit that servers "MUST sanitize file paths to prevent directory traversal attacks" — the same discipline applies to every filesystem-touching Tool here, not just to Resources, and is worth an explicit test case (a session ID like `../../etc/passwd`) in the fixture suite from §9. *Risk: medium if unaddressed, low-cost to close.*
- **Concurrent writers.** Vivechak's own design assumes parallel Layer‑0 sessions; if two agent processes (or the same agent racing itself) call a decision-recording tool against the same `DECISIONS.md` at once, plain "read, modify, write" file handling can lose an update. Recommend atomic writes (write-temp, `rename`) plus a simple advisory lock file per workspace, and revisit the SQLite alternative from §2 if this ever becomes a frequent, not occasional, pattern — a natural **review trigger** for whatever ADR records this decision: *"re-evaluate if concurrent-write conflicts are observed in practice, or if the roadmap's multi-agent-debate phase ships."*
- **Spec churn rate.** Between this session's fetches, the spec moved through at least four dated versions in roughly ten months (2025‑06‑18 → 2025‑11‑25 → 2026‑07‑28) with one already-Final backward-incompatible rewrite (statelessness) inside that window. *Risk: ongoing, not one-time* — mitigate by depending on the Go SDK's abstractions rather than hand-rolling any wire-level behavior, tracking SDK release notes each upgrade (the SDK's own version-compatibility table is the fastest way to see what changed), and treating anything this document says about a specific SEP number as subject to further amendment.
- **Scope note (not a risk, a boundary):** this research deliberately did not investigate OAuth/remote-server authorization, MCP Apps (interactive UI), or the Skills/"Skills over MCP" working group's positioning relative to tool-based guidance — all adjacent, all out of the brief's stated scope, but the last one in particular (an active MCP working group charter exists for it) is worth a dedicated look if the "guide the agent" problem ever outgrows what tool results alone can carry.
- **Suggested `door_type` for D‑001, if it inherits this research's framing:** classify the *state-storage medium* (files vs. DB vs. memory) as effectively one-way in practice even though it is technically swappable later, because migrating an in-use project's history off a Markdown+YAML contract would be disruptive; classify the *Guide/Worker response-shape* choice as two-way, since it can be adjusted tool-by-tool without touching stored data.
